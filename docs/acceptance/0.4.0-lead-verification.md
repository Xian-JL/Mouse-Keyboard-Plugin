## 4 真机发现（按严重度）

**F1（中）UWP 内容元素不可点击、持续重绘窗口不可坐标点击**
- 现象：对 `ApplicationFrameHost` 承载的设置窗口，`elementName=搜索框/主页` 三次均 `STATE_CHANGED / element-identity-or-bounds`；坐标点击两次均 `STATE_CHANGED / significant-target-change`（整窗 7,121 像素变化）。
- 佐证：同窗口 `waitFor pixel stable` 在 1.5 s 内不收敛（`matched:false`），说明该窗口内容确实在持续重绘。
- 判定：这是 0.3.x 既有保守策略（观察后内容变化即拒绝）在 UWP 上的表现，**不是 0.4.0 回归**；但对"常规 Windows 设置页"这类目标，可操作性实际很低。Win32 标题栏按钮可点，说明元素定位本身可用。
- 建议（不阻塞本次）：为 UWP 增加"内容重绘窗口"的白名单/容忍策略；或在文档里明确"持续动画窗口建议坐标点击前先等 stable，等不到就换目标"。

**F2（中）`mk_observe targets` 会使先前 target id 失效**
- 现象：拿到 target 后再次调用 `targets`，旧 id 立刻 `TARGET_CHANGED`，`requiredAction=rebegin`。本次因此中断两次。
- 影响：模型若"先刷新列表再操作"，会反复失效。
- 建议：要么文档写明"targets 之后必须重新 observe"，要么让 discover 不使旧 id 失效。

**F3（低-中）region 作用域快照上的点击，后置观察报 INVALID_COORDINATE**
- 现象：用 `region` 观察得到 600×260 快照后点标题栏按钮，`execution=sent`，但 `observationError{INVALID_COORDINATE}`（点击点落在 region 外），`observation=null`。
- 说明：安全语义正确（sent / 不重放），但"点一下就拿不到后置观察"对连续操作不友好。
- 建议：后置观察回退到全窗口，或 region 快照上禁止点击并明确报错。

**F4（低）cloke 的 UWP 子窗口会返回错误画面**
- 现象：对 `SystemSettings.exe` 的 `设置` 窗口做 `observe window`，`window.foreground=true`、`captureRect` 是该窗口矩形，但 PNG 内容实际是前台窗口（当时是 DSH）的画面；改选 `ApplicationFrameHost.exe` 的 `设置` 窗口后画面正确。
- 建议：发现阶段过滤 cloaked/UWP 子窗口，或在 `window` 回执里标注 `cloaked=true`。

**新发现**

- **F5（P0，阻塞）输入在 64 码点处被中断，`settleMs/paceMs` 救不了。**
  `helper/Server.cs:300` 的循环在**每个 32 字符块之前**调用 `RequireFocus(snap,w)`，而 `RequireFocus`（`:238`）用 `Native.SameElementState(before,current)` 把"元素当前状态"与**快照时**的状态比对。xterm 的隐藏 textarea 会随光标移动（实测 rect left 依次 1445→1780→2024→2452→2650），我们的输入本身就在改变它；到第 3 块时比对失败 → `STATE_CHANGED`，已发送的 64 码点保留、不再继续。`inputMode=unicode` 与 `scancode` 表现一致。
  **建议**：`type`/`key` 的多块循环里，复验只做"身份 + 所属窗口 + 前台 + 启用/可见"（不比对会自变的 value 与 rect）；或把已发送文本作为期望基线参与比对。这与 FR-01 的目标（长文本一次送达）直接冲突，必须修。
- **F6（P0，阻塞）画布目标无法点击：整窗像素比对把"画面自身刷新"判成 STATE_CHANGED。**

  **建议**：对 `ControlType.Image`/画布类目标，点击前的比对只覆盖落点邻域（现有 12 DIP 逻辑）而不是整窗；或把"光标闪烁"纳入容差（现在只归一化系统光标的小矩形）。
